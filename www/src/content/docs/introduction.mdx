oasts is a compiler.
It reads an OpenAPI 3.0 or 3.1 document and writes TypeScript you commit and review: per-operation types, a zero-dependency fetch client, Zod schemas, standalone validators, TanStack Query descriptors, and MSW handlers — all derived from one model, so they cannot disagree about your API.

## What makes it different

<CardGrid>
  <Card title="Failure-complete results" icon="ph:git-branch">
    Every call returns a discriminated union covering documented responses, undocumented statuses, network failures, and decode failures — not just the 2xx happy path.
    One `switch` reaches every case, and exhaustiveness checking proves it.
  </Card>
  <Card title="Byte-identical output" icon="ph:fingerprint">
    Same document bytes, same config, same version, same consumer `tsconfig.json` ⇒ the same bytes on every machine and OS.
    Generated code is meant to be committed; `oasts generate --check` makes drift a CI failure.
    See [Determinism](/concepts/determinism).
  </Card>
  <Card title="Auth the compiler checks" icon="ph:lock-key">
    An operation's security requirements compile into its call signature, so calling one whose auth you never configured is a type error rather than a 401 you find in staging.
  </Card>
  <Card title="Nothing in your bundle" icon="ph:feather">
    The typed fetch client is emitted next to your types.
    No runtime package to version-match, nothing added to your dependency tree.
  </Card>
</CardGrid>

## Performance

Measured, not promised: the in-repo benchmark harness compiles GitHub's full OpenAPI spec to types in ~80 ms — warm p50 of end-to-end `oasts generate` runs on the reference container — with every run gated on repeatability.
