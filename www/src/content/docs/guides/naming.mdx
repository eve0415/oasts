## File names

`naming.fileCase` controls the filename derived from an `operationId` or schema name. Word
boundaries come from any non-alphanumeric character in the source name — `-`, `_`, `.`, `/` —
**and never from case transitions**:

| `fileCase` | `get_pet_by_id` | `getPet` |
| --- | --- | --- |
| `kebab` *(default)* | `get-pet-by-id.ts` | `getpet.ts` |
| `snake` | `get_pet_by_id.ts` | `getpet.ts` |
| `camel` | `getPetById.ts` | `getPet.ts` |
| `pascal` | `GetPetById.ts` | `GetPet.ts` |
| `preserve` | `get-pet-by-id.ts` | `getPet.ts` |

```yaml title="oasts.yaml"
naming:
  fileCase: kebab
```

`kebab` and `snake` lowercase the token; `camel` and `pascal` join the tokens and capitalize. So an
already-camelCase `operationId` looks unchanged under `camel`/`preserve` and runs together under
`kebab`/`snake` — `getPet` becomes `getpet.ts`, not `get-pet.ts`, because there is no separator to
split on.

<Aside type="caution">
  Renaming the operation to introduce a separator moves the filename *and* the type names with it —
  `operations: { getPet: get_pet }` gives you `get-pet.ts` and `Get_petRequest`. The override sets
  one identifier and everything derives from it; it is not a filename-only knob.
</Aside>

## Identifiers

| Setting | Values | Default |
| --- | --- | --- |
| `operationCase` | `camel`, `preserve` | `camel` |
| `enumMemberCase` | `pascal`, `camel`, `screamingSnake`, `preserve` | `pascal` |
| `typePrefix`, `typeSuffix` | any string | empty |

```yaml title="oasts.yaml"
naming:
  operationCase: camel
  enumMemberCase: screamingSnake
  typePrefix: Api
```

<Aside type="note" title="Two settings are pinned">
  `typeCase` accepts only `pascal` and `propertyCase` only `preserve`. Type names are TypeScript
  identifiers, where PascalCase is the universal convention; **property names are wire names**, and
  re-casing them would make the emitted type describe a payload your API does not send. They exist
  in the schema so the surface can grow, and any other value is a config error today.
</Aside>

## Collisions in names your document owns are refused

Two schemas, operations or webhooks that normalize to the same identifier stop the build, with both
offenders named. oasts never picks a winner for you.

The reason is ambiguity. A suffix like `Pet2` would attach to whichever of the two declarations the
walk reached first, and nothing in your document says which one you meant it for. A refusal you
resolve once, in `naming.overrides`, cannot move.

Names the *compiler* invented are different. A request/response variant that collides with a
declared component is re-emitted as `{Name}Body`, and a wire twin as `{Name}WireValue`, each with a
warning saying so and generation continuing — your document owns its name, so the invented one
yields. Only when that replacement is also taken is the document refused.

## Overrides

`naming.overrides` is the remedy, keyed by the **raw wire name** rather than the derived one:

```yaml title="oasts.yaml"
naming:
  overrides:
    schemas:
      Pet: PetModel                    # a components/schemas key, or a document-root schema's file stem
    operations:
      getPet: fetchPet                 # an operationId
    pathSegments:
      foo_bar: fooBarUnderscore        # raw URL path segment text
    webhooks:
      "pet.created": PetCreatedHook    # a document webhooks key
    callbacks:
      onData: OnDataCallback           # an operation callbacks key
    schemasBySource:
      "workspace/vendor/openapi.yaml#/components/schemas/Pet": VendorPet
```

`schemasBySource` is keyed by `<source_id>#<json_pointer>` and exists for the case two documents
contribute a schema with the same name — the plain `schemas` key cannot tell them apart. A local
`source_id` is `workspace/<path>` relative to the workspace root, or `allow/<n>/<path>` for a
`local.allowPaths` root.

<Aside type="caution">
  An override that matches nothing is an error too — for `schemas`, `schemasBySource`, `operations`,
  `webhooks` and `callbacks`, the same rule that makes filters fail loudly applies, and for the same
  reason: a stale override is a rename you think is happening and is not. `pathSegments` is the
  exception. Only the TanStack artifact consumes it, so a stale entry is an `OASTS6303` **warning**
  raised there, and is silent entirely when that artifact is off.
</Aside>

## Which collisions you might meet

| Code | Severity | Collision |
| --- | --- | --- |
| `OASTS4102` | error | A component import whose role-derived replacement is taken by another import, or by a declaration in that module |
| `OASTS4103` | error | A request/response variant's replacement is a declared component or another variant's replacement |
| `OASTS4104` | warning | A `{Name}Wire` twin collides with a declared component — the document owns its name, so the twin is emitted as `{Name}WireValue` and generation continues |
| `OASTS4105` | error | `{Name}WireValue` is also declared, so nothing compiler-invented is left to move |
| `OASTS6302` | error | Two path nodes normalize to the same TanStack key-factory name, or that name shadows one of the module's imports |

The full list is in [Diagnostics](/concepts/diagnostics#names-the-compiler-will-not-invent).
