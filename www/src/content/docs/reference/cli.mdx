The package is `@oasts/cli`; the command it installs is `oasts`.

```text
Usage: oasts <command> [options]

Commands:
  generate           Generate configured artifacts
  check              Validate configuration and input without emitting
  watch              Watch inputs and regenerate until interrupted

Options:
  --config <path>    Use an explicit configuration file
  --check            With generate: check committed output without writing
  --spec <name>      Build only the named workspace spec; repeatable.
                     Omit it to build every spec the configuration declares
```

## `oasts generate`

Reads your document and writes every enabled artifact under `output`.

<PackageManagers pkg="oasts" type="exec" args="generate" />

### `--check`

Does everything `generate` does except writing.
Any difference between what would be written and what is committed exits non-zero and reports the drift.
This is the CI form:

<PackageManagers pkg="oasts" type="exec" args="generate --check" />

Because output is [byte-identical](/concepts/determinism) for the same inputs, `--check` is a real gate, not a heuristic — see [Determinism](/concepts/determinism).

## `oasts check`

Validates the configuration and the input document, and reports every diagnostic, without writing anything.

<PackageManagers pkg="oasts" type="exec" args="check" />

Use it to see what your document produces — including every warning about an operation an artifact had to skip — before committing to a run.

## `oasts watch`

Does what `generate` does, then keeps going: it watches everything the compile read and compiles again whenever any of it changes, until you interrupt it.

<PackageManagers pkg="oasts" type="exec" args="watch" />

A recompile is a cold compile — the whole run is redone from the configuration down, so what a watch session writes is byte for byte what `oasts generate` would have written.
Nothing is cached and nothing is incremental.

### What it watches

Everything the last compile actually read or looked for, which is wider than the document graph:

- the configuration file, and every other name [discovery](#config-discovery) would have accepted in the same directory, so a second `oasts.*` appearing is noticed;
- the entry document and every local document its `$ref`s reach;
- the consumer's `tsconfig.json`, every file its `extends` chain reaches, and each `tsconfig.json` the [ancestor walk](/reference/configuration#typescript) looked for inside the workspace and did not find;
- the `node_modules/zod` and `node_modules/msw` manifests the peer-version warnings were read from.

The set is recomputed after every compile, so adding a `$ref` starts watching the file it points at.
Directories are watched rather than individual files, which is what makes an editor's save-and-rename visible, and events are matched against that set before any of them counts — so the artifacts a run writes never wake the next one.
When the operating system reports that it lost events without saying which, the session recompiles rather than guessing, because the one thing a watch may not do is serve output that is out of date.

<Aside type="note" title="Three things a session will not pick up">
  A peer package **appearing** where none was installed: the manifest is watched only once one has been found, so installing `zod` mid-session does not re-run the version check until you restart.
  A `tsconfig.json` appearing **above** the workspace root: the ancestor walk reads that far, but a project with none anywhere would otherwise have the session watching every directory up to the filesystem root, so only the probes inside the workspace are followed.
  And on the Node CLI, a module your `oasts.config.ts` **imports**: the config file itself is re-evaluated on every cycle, but modules it pulls in stay cached for the life of the process.
</Aside>

<Aside type="note" title="One difference between the two CLIs">
  When the operating system's own event queue overflows, it reports that it lost events without saying which — and the standalone `oasts` binary recompiles on it.
  The Node CLI cannot: `node:fs.watch` does not surface that condition at all, so on a burst large enough to overflow the queue a Node session can miss changes until the next edit.
  Everything else — what is watched, what counts as a change, how failures end the session — is the same on both.
</Aside>

### Diagnostics do not end the session

A compile that fails is reported and the session keeps waiting.
A typo in a document, a config that stopped parsing, a `$ref` to a file that is not there yet — all of them print and then wait for the next edit.
While a compile is failing the session also widens what counts as a change, so creating the file it was missing brings it straight back — anywhere except inside the output tree, which stays filtered to what the compile read so that a run's own artifacts can never be mistaken for a fix.

There is no successful exit: `oasts watch` runs until you interrupt it.
What ends it on its own is losing the ability to answer for freshness, which exits `2` with `OASTS1031`: a directory it was told to watch and could not, a compile that reported nothing to watch, or a watcher that stopped reporting underneath it.
A watch that cannot see one of its inputs would quietly serve stale output, which is worse than stopping.

### Coalescing

A single save is several filesystem events, and an edit that lands mid-compile queues behind it.
Both are coalesced: the session waits for the tree to go quiet before starting a compile, so one save is one recompile.
How long it waits is [`watch.debounceMs`](/reference/configuration#watch), 100 ms by default.

Only events that would themselves have started a compile keep that wait open, so a bundler writing into your output tree cannot postpone a recompile it is not part of.
And the wait is capped at a second regardless: churn can delay a compile, but nothing can cancel one.

## `--spec`

Builds only the named spec of a [workspace configuration](/guides/workspaces), and repeats:

<PackageManagers pkg="oasts" type="exec" args="generate --spec billing --spec users" />

Omitting it builds every spec the configuration declares, in lexicographic name order.
A name the configuration does not declare exits `2` with `OASTS0294`, which lists the names it does.
Against a configuration that declares a single spec at the root, `--spec` exits `2` with `OASTS0295`.

`watch` takes it too: a session compiles the specs you selected and watches exactly what those compiles read.

## `--config`

Points at an explicit configuration file:

<PackageManagers pkg="oasts" type="exec" args="generate --config ./config/oasts.yaml" />

Paths inside the config (`input.path`, `output`, and the rest) resolve relative to the **config file's** directory, not to your working directory.
Moving the config moves everything with it.

## Config discovery

With no `--config`, oasts looks in the current directory for exactly these names:

```text
oasts.config.ts   oasts.config.mts   oasts.config.cts
oasts.config.js   oasts.config.mjs   oasts.config.cjs
oasts.yaml        oasts.json
```

<Aside type="caution" title="Exactly one, or it is an error">
  Discovery does not apply a precedence order.
  Finding two candidates — say `oasts.yaml` next to `oasts.config.ts` — fails, and so does finding none.
  Note also that `oasts.yml` is **not** in the list; the spelling is `oasts.yaml`.
</Aside>

A `oasts.config.ts` is evaluated as a module, which means discovering one and running it executes whatever code it contains — the same trust you extend to any `*.config.ts` in your toolchain, and the one real difference from `oasts.yaml`, which is only ever read as data.
It is imported exactly once per invocation; see [Determinism](/concepts/determinism) for what that means for output stability.
Import `defineConfig` from the package for editor completion and a compile-time check of the whole config:

```ts title="oasts.config.ts"
import { defineConfig } from "@oasts/cli";

export default defineConfig({
  schemaVersion: 1,
  input: { path: "./openapi.yaml" },
  output: "./generated",
  artifacts: { types: true, client: true },
  validation: { engine: "off", unchecked: "allow" },
});
```

The client artifact requires an explicit `validation` block; `engine: "off"` opts out of boundary checking.
See [Validation](/artifacts/validation) for the other engines.

The `.yaml` and `.json` forms are validated against the published JSON Schema instead — see [Configuration](/reference/configuration).

## Exit codes

The compiler ends a run with one of three:

| Code | Meaning |
| --- | --- |
| `0` | Success. Warnings may still have been printed. |
| `1` | An **input** diagnostic — something about the document itself. Also drift under `--check`. |
| `2` | A **config** diagnostic — usage, the config file, or any file oasts had to read or write. |

The split is the diagnostic's category.
It is not a severity ranking, not the stage the diagnostic came from, and not how far the run got.
Every diagnostic carries a category of its own, and the run exits on the highest code it saw.
Two consequences follow from that, and both surprise people:

**Anything to do with files is `2`, including the write.**
Failing to write an artifact — or to read your committed output back under `--check` — is a config-category diagnostic.
So a run that read your document, compiled it, and then tripped over the output tree exits `2`, not `1`.

**One config-category error re-codes the whole run.**
When a config diagnostic and a content diagnostic land together, both are reported and the exit code is `2`.
The way you meet this by accident is the default `typescript.tsconfig: auto`: a broken `tsconfig.json` sitting in your workspace gets discovered, read, and reported, which turns what would have been a `1` into a `2` without anything changing in your document.

Warnings never change the exit code.
If you want a warning to fail your build, grep the output or gate on `oasts check` in a step of its own.

### Codes oasts did not choose

Anything outside `0`–`2` means the run never reached a verdict.
A refusal always prints `error[OASTSnnnn]`; these do not, which is how you tell them apart:

- **`134`** — the compiler crashed. You get a Rust panic message and no diagnostic. (Invoking the native binary directly gives `101` instead.) That is always a bug — please report it along with the document that provoked it.
- **anything else** — `oasts.config.ts` is evaluated as a module, so your config can end the process itself. A `process.exit(3)` in there is exit `3`, before oasts has looked at anything.

## What the package exports

`@oasts/cli`'s public entry is the config surface — `defineConfig` and the `UserConfig` types, both generated from the same schema the YAML form is validated against.
The compiler itself is a native module loaded through napi, so there is no JavaScript reimplementation that could drift from it.
