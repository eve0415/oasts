oasts is a compiler with three stages, and understanding them explains most of its behaviour.

<Steps>
  <Step title="Load">
    The document is read from `input.path` or `input.url`, along with everything it `$ref`s. Local
    references stay inside a trust boundary you control; the graph is bounded by `limits`.
  </Step>
  <Step title="Model">
    One versioned model is built from the whole document: schemas, operations, parameters, media
    types, security requirements. [Filters](/guides/filters) narrow it here, once, before anything
    is emitted.
  </Step>
  <Step title="Emit">
    Every enabled [artifact](/artifacts) is projected from that one model. Types, client, zod,
    validators, TanStack descriptors and MSW handlers are all views of the same thing.
  </Step>
</Steps>

## One model, many artifacts

This is why the artifacts cannot disagree. The client's request encoder and the MSW handler's
request decoder are the same serialization rules run in opposite directions. The validators and the
Zod schemas are two renderings of the same checks. Turning on a fifth artifact never re-interprets
your document; it adds a projection of a model that already exists.

It is also why a refusal in one artifact does not cost you the others. When MSW cannot express an
operation's path, that operation gets no handler and a warning — the types, client and validators
for it are unaffected.

## Output is a build artifact you commit

oasts does not run in your app. It writes TypeScript to a directory, and that directory is source
you review in a pull request. Given the same document, config and oasts version, the bytes are
identical on every machine — so a diff in generated output means your API changed, and CI can
enforce that with `oasts generate --check`.

<Aside type="note">
  This is the opposite of a runtime SDK. There is no oasts package in your dependency tree at
  runtime, nothing to version-match, and no code path that behaves differently in production than
  the one you read in review. See [Determinism](/concepts/determinism).
</Aside>

## Refusals are loud, never silent

The compiler will not invent a name to resolve a collision, will not widen a type past what the
document says, and will not quietly drop a pattern that stopped matching. Each of those is a
[diagnostic](/concepts/diagnostics) with a code and a source pointer, and most of them fail the
build.

The reasoning is that all three failure modes are invisible at the call site. A compiler-invented
suffix shifts the next time the document changes; a type widened to `unknown` type-checks and then
breaks at runtime; a filter that matches nothing shrinks your client without a diff anyone reads.

## What you configure, and what you don't

You configure **what to generate** — which artifacts, which slice of the document, what shape the
types take, where files land. You do not configure formatting, layout of the emitted code, or
whether a check runs; those are fixed so output stays comparable.
