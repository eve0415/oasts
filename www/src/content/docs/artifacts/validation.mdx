oasts emits two validation artifacts.
They are standalone — you can generate either without a client — and the client can call whichever one you pick.

<CardGrid>
  <Card title="validators" icon="ph:shield-check">
    Dependency-free generated validators implementing Standard Schema v1.
    Nothing to install.
  </Card>
  <Card title="zod" icon="ph:package">
    Zod v4 schemas you can hand to anything that speaks Zod.
    Needs `zod` ^4.4.0 in your project.
  </Card>
</CardGrid>

```yaml title="oasts.yaml"
artifacts:
  types: true
  validators: true
  zod: true
```

Both are compiled from the same model and share one capability matrix, and each engine's frozen conformance vectors hold it to the same verdicts — for any value the two agree on pass or fail.
Success values agree structurally, not by identity: the generated validators hand back the input by reference, while Zod reconstructs the object with declared properties first.
Issue messages and issue grouping are engine-local and deliberately not pinned.
Validation-only keywords that the [types artifact](/artifacts/types) cannot express — numeric ranges, string patterns, length bounds, string formats — are exactly what these two carry.

## Wiring one into the client

```yaml title="oasts.yaml"
artifacts:
  types: true
  client: true
  validators: true
validation:
  engine: generated    # off | zod | generated
  request: true
  response: true
  unchecked: allow     # warn | error | allow
```

`engine` selects the implementation the client calls: `generated` uses the validators artifact, `zod` uses the Zod schemas, `off` does no runtime checking.
There is no default — with the client artifact enabled, `validation.engine` is required, so the choice is always written down.
`request` and `response` choose the positions.

A failed check comes back as a result, not a throw — a `request-validation` or `response-validation` outcome carrying its issues, branched in the same `switch` as everything else.
See [Client](/artifacts/client#failure-complete-results).

`unchecked` is the policy for successful response data that is decoded and then never checked against the OpenAPI schema — because `response: false` turns response validation off, or because the branch is a raw byte stream, which carries no schema to check.
`allow` passes it through, `warn` prints a generation-time warning and continues, and `error` refuses.
The default is `warn`.

<Aside type="note">
  Validators only ever observe wire values.
  When a [date representation](/guides/dates) is configured, conversion happens after response validation and before request validation, so a `Date` or `Temporal` value never reaches a schema.
</Aside>

## Zod flavor

The zod artifact imports classic `zod` by default.
Set `zod.flavor: mini` to import `zod/mini` instead — the tree-shakable entry point, same package, same `^4.4.0` peer range, no extra dependency:

```yaml title="oasts.yaml"
artifacts:
  types: true
  zod: true
zod:
  flavor: mini
```

Both flavors share one parsing core, so verdicts and parsed values are identical.
What changes is what your bundler can drop.
Each row below is one esbuild bundle over the named entry points from the GitHub spec's generated artifact, minified and gzipped:

| bundle | `zod` | `zod/mini` |
| --- | --- | --- |
| `meta-get-octocat` (smallest operation) | 15.9 kB | 2.8 kB |
| `dependabot-list-alerts-for-repo` (largest operation) | 22.3 kB | 8.1 kB |
| the first thirty operations together | 25.5 kB | 11.4 kB |

Zod itself dominates a small bundle and amortizes across a large one, which is why the smallest operation gains the most proportionally.

Those are figures from a one-off measurement, not numbers any gate holds, so read the ratio between the columns rather than the absolute kilobytes — your own spec, bundler and zod version will move them.

Pick `classic` if you hand the emitted schemas to something that expects a classic `ZodType` — under `mini` they are `ZodMiniType`.

## String formats

A `format` is only an annotation in JSON Schema, but a handful of them describe a syntax precise enough to check, and both engines assert those.
Each one is named against the specification it implements, because "a valid email address" is not one thing:

| `format` | What is asserted |
| --- | --- |
| `date-time` | RFC 3339 `date-time`, with a real calendar date, a required offset, and a leap second accepted |
| `date` | RFC 3339 `full-date`, with real calendar validation |
| `time` | RFC 3339 `full-time`; a `Z` or numeric offset is required |
| `duration` | RFC 3339 Appendix A `duration`: unsigned integer components in nested order, or a bare week count |
| `uuid` | 8-4-4-4-12 hexadecimal groups, any version, case-insensitive |
| `email` | RFC 5321 `Mailbox`: a dot-atom or quoted-string local part, and either a host name or a bracketed IPv4/IPv6 address literal |
| `hostname` | RFC 1123 host name: dot-separated letter-digit-hyphen labels of at most 63 characters, at most 253 overall |
| `ipv4` | Four decimal octets in 0..255, each written without a leading zero |
| `ipv6` | RFC 4291 §2.2, including the `::` elision and a dotted-quad supplying the low-order 32 bits, which only the end of the address may carry |
| `uri` | RFC 3986 §3 URI: a scheme is required, and every component is checked against its character set |
| `uri-reference` | RFC 3986 §4.1 URI-reference: a URI, or a relative reference |

`int32` is asserted too, on integer schemas, as the signed 32-bit range.

The checks are deliberately syntactic and deliberately permissive, because a validator that rejects a legitimate value is the worse failure.
One deviation is deliberate and worth recording. An `ipv4` octet written with a leading zero, such as `010.0.0.1`, is rejected, even though RFC 2673 §3.2 defines an octet as `1*3DIGIT` and so permits it. A leading zero is read as octal by some resolvers and as decimal by others, so `010.0.0.1` and `10.0.0.1` can name different hosts to different readers, which turns any allowlist built on this check into a bypass. The same string is rejected wherever it appears as the dotted tail of an IPv6 literal, and there RFC 3986's `dec-octet` production forbids it outright.

Three further consequences are worth knowing: a `hostname` label beginning `xn--` passes as ordinary letter-digit-hyphen text, since IDNA validity would need the Unicode tables that this runtime does not ship; an `email` address is checked as ASCII, so SMTPUTF8 addresses and RFC 5322 comments are rejected; and an IPv6 zone identifier such as `%eth0` is not part of the address production, so it is rejected.

No other string `format` is asserted — `password`, `byte`, `binary` and the `idn-` and `iri-` families are carried as annotations, and reach the generated code only as a doc comment.
`regex` is among them on purpose: deciding it means compiling a caller-supplied pattern at validation time, which hands untrusted input to the host regular-expression engine, and the verdict would then follow whichever JavaScript engine happens to run the check.

A `format` is asserted only where `string` is among the schema's declared types, and the check sits inside the string branch of the emitted narrowing — so a nullable string is checked when it holds a string and left alone when it holds `null`, while a schema with no declared type is not checked at all.

## Discriminators are annotations

Neither engine consults a `discriminator` to reach a verdict.
It is an annotation, and letting it decide would mean rejecting payloads the underlying schemas accept.
This is also why [`types.discriminatedUnions: tagged`](/artifacts/types#discriminated-unions) is opt-in rather than the default.
