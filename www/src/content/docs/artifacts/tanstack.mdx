TanStack descriptors are built on the client, so the `validation` block the [client](/artifacts/client) requires comes along with them.

Almost every operation gets a descriptor — a plain `{ queryKey, queryFn }` or `{ mutationKey, mutationFn }` object you spread into whatever adapter you already use.
No hooks, no peer dependency, no React context to carry the transport: generated code imports nothing from TanStack, so the same descriptor works in React, Solid, Svelte, a route loader, or a prefetch.

```ts
import { useQuery } from "@tanstack/react-query";
import { getPetQuery } from "./generated/tanstack/operations/getpet.js";

const pet = useQuery(getPetQuery(transport, { path: { petId } }));
```

`queryFn` resolves the response payload, so `pet.data` is your `Pet` — not an envelope you have to unwrap twice.
Errors reject with the typed `ApiError` for that operation, and each module exports `{Operation}QueryKey`, `{Operation}QueryData` and `{Operation}QueryError` so you can name them.

## Keys are hierarchical

Query keys come from the URL path template, so a prefix invalidates everything beneath it:

```ts
import { keys, apiPetsAll } from "./generated/tanstack/keys.js";

queryClient.invalidateQueries({ queryKey: apiPetsAll });     // every pet query
queryClient.setQueryDefaults(apiPetsAll, { staleTime: 30_000 });
keys.pets.byPetId.all(petId);                                 // everything under one pet
```

A literal path segment contributes a string and a parameter contributes a single-key object.
So `/pets/mine` and `/pets/{petId}` with `petId = "mine"` share every ancestor — `["api", "pets"]`, which is exactly what makes prefix invalidation work — and then diverge at the segment where `"mine"` meets `{ petId: "mine" }`.
A string never equals an object, so nothing below that point can collide the way a template-string key can.
An optional path parameter you leave `undefined` contributes `[]`, which is a segment of its own rather than a hole.

Every path node is also exported as a flat binding (`apiPetsAll`, `apiPetsByPetId`).
A query module imports one leaf, and a mutation imports only the chain it invalidates, so bundling a single descriptor does not drag in the rest of the spec's key data; import the composed `keys` object when you want the whole tree.

## Invalidating after a mutation

Each mutation exports a companion that takes the same input and returns the keys it structurally affects, broadest first:

```ts
import { updatePetMutation, updatePetMutationAffects } from "./generated/tanstack/operations/updatepet.js";

useMutation({
  ...updatePetMutation(transport),
  onSuccess: (_data, input) => {
    for (const key of updatePetMutationAffects(input)) {
      queryClient.invalidateQueries({ queryKey: key });
    }
  },
});
```

It takes the input, so it always has the path parameters it needs.
It is a structural derivation from the path template, never a claim about what your API means — compose it with what you know.

<Aside type="caution">
  These are **prefix** keys.
  A query that carried query, header, cookie or body input has those appended as a further key element, so `exact: true` against the entity entry matches only the unfiltered query — invalidate without it to catch every filtered variant of the same resource.
</Aside>

## What does not get a descriptor

A read gets one only when **every** documented success response carries a buffered body.
Three things disqualify an operation, and each emits an `OASTS6301` warning naming it rather than a descriptor that fails at runtime:

- **A success branch with no payload.** A `HEAD`, a 204-only `GET`, and a `GET` returning 200 *or* 204 all fail this — the last one is the easy one to miss, because it only resolves `undefined` on the days the server picks the 204, and TanStack rejects a `queryFn` that resolves `undefined`.
- **No documented success response at all.** There is nothing for a query function to resolve.
- **[Streaming](/guides/streaming), in either direction.** A stream is consumable once: a response stream cannot be handed to two cache readers, and a request stream cannot survive a retry.

The first two are read-only concerns — a 204 `DELETE` still gets a mutation descriptor, because mutations may resolve `undefined`.
Streaming is not: a streaming operation gets no descriptor on either side.

Infinite queries are not generated either.
OpenAPI has no pagination vocabulary, so any such support would be a guess about your API that fails silently at runtime; write `infiniteQueryOptions` by hand over the same call.

## When two paths would fight over a name

Key bindings are derived from path text, so `/foo-bar` and `/foo_bar` want the same name — and so do `/foo/bar` and `/foo-bar`, a segment named `all`, and anything that normalizes to a name the generated module already uses.
No key binding is a name your document declares — the compiler composes each one from your namespace and the path text — so the same rule that governs a generated `{Name}Wire` applies: the invented name yields, with an `OASTS6304` warning naming both, and generation continues.
The loser of each race takes the lowest free numeric suffix: `fooBar` and `fooBar2`, `all` and `all2`.
Both paths keep a key of their own, and each key still carries its own raw segment text, so two paths never share a cache entry however they end up named.

Which competitor keeps the bare name is decided by one walk — configured members first, then derived ones, siblings in raw segment order, path nodes in pre-order — so it is a property of the document rather than of the order operations appear in, and two runs over one document name everything identically.
A name you configured never moves; a derived one still can, because adding a path that sorts earlier shifts the suffix onto a binding that did not have one.
That is what the warning is for, and pinning the names you import by hand is what stops it — `naming.overrides.pathSegments`, keyed by the raw segment text:

```yaml title="oasts.yaml"
naming:
  overrides:
    pathSegments:
      foo_bar: fooBarUnderscore
```

Two things are still refused, because no name resolves them.
Two declared paths whose key elements are identical — `/pets` and `/pets/`, where the separator-only segment contributes nothing — would share one cache entry whatever their bindings are called.
And a segment whose text yields no identifier at all, such as one with no ASCII form, has no derived name to put a suffix on; an override is the only thing that can give it one.
